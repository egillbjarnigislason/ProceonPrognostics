Proceon Prognostics
Predictive maintenance · project brief

Forecast a motor failing before it stops the line.

A training-and-inference system that learns a machine's failure signature from the signals it already emits — temperature, vibration, current — and lets every manual inspection sharpen the next prediction. Built to start as a weekend notebook and grow, one honest step at a time, into an agent that reads the predictions and recommends the fix.

Status: draft for discussion Builds on: VisionFramework core Runtime: LibTorch · ONNX Scope: P0 → P5
01 · What this is

One kernel, six sizes

The whole system is one small idea wrapped in progressively more machinery: slide a window over the sensor stream, score it, and decide. Everything else — the alerting, the feedback loop, the fleet view, the agent — wraps that kernel without replacing it. That is what lets the project scale down as easily as up: strip the wrappers and the P0 core still runs on a laptop.

It deliberately reuses the shape of the existing VisionFramework: the same config-driven task: dispatch, the same phase-1-warmup → phase-2-finetune training loop, the same run/checkpoint management, and the same LibTorch → ONNX export path. A prognostics task is a new data loader and a temporal model bolted onto proven scaffolding — not a greenfield rebuild. Whether it lives as a third task: or a sibling repo sharing that core is a packaging choice, addressed under scaling.

02 · Framing the problem

Decide what "failure" means before you model it

The single decision that governs the whole design is what the model predicts. Predictive maintenance data is almost always lopsided — thousands of healthy hours per real breakdown — so the right framing depends on how much failure history you actually hold. Pick deliberately; each one wants different labels, losses, and datasets.

Framing A

Horizon classification

“Will this motor fail within the next N hours?” Maps almost directly onto the existing classification head. Simplest to ship — but hungry for labeled failure events, which you rarely have on day one.

Framing B

RUL regression

Predict remaining useful life — hours-to-failure. The most actionable output for scheduling maintenance, but it needs run-to-failure histories to build the target.

Framing C

Anomaly detection

Train only on healthy operation, flag deviation. Sidesteps the “too few failures” problem entirely — the realistic cold-start default until enough confirmed failures accumulate.

The cold-start reality

You will not have labeled failures at the start. Begin with Framing C (anomaly) on healthy line data, and let the calibration loop below convert every inspected alert into the labeled examples that eventually unlock Framing A or B. The system is designed so this transition needs no rewrite — only more data.

03 · Architecture

Training and inference share one pipeline

Two paths, one set of parts. The inference path (top) turns a live sensor stream into decisions. The training path (bottom) turns labeled windows into the ONNX model the inference path runs. They meet at the model, and they close through the feedback loop in §04.

Component by component, the parts that are new versus reused:

  • Windowing loader (new) — slides fixed windows over each asset's multivariate stream, normalizing per channel on training statistics only. At high sample rates an FFT/spectrogram front-end usually beats raw time series, since fault signatures live in the frequency domain.
  • Temporal model (new) — a 1-D CNN / TCN to start (fast, exports cleanly), an LSTM/GRU if long memory proves necessary. Replaces the image backbone; everything downstream is unchanged.
  • Training loop, run management, ONNX export (reused) — lifted from VisionFramework. A temporal LibTorch module exports to ONNX exactly like the CNN, so production inference stays byte-identical to training.
  • Calibrated threshold (new, small) — the score-to-decision cutoff, tuned by the feedback loop rather than hard-coded.
04 · The calibration loop

Every inspection makes the next call better

A forecast is only useful if the floor trusts it, and trust dies with false alarms. So the design treats a manual inspection saying “nothing wrong here” as a first-class input, not a complaint. Each alert becomes a work order; each verdict feeds two loops running at different speeds.

Why the split matters: retraining on every click is slow, unstable, and invites the model to chase one inspector's noise. Recalibrating a threshold is cheap, reversible, and immediately felt on the floor. So the loop separates “this alert was wrong, be less trigger-happy here” (fast) from “here is a genuinely new example to learn from” (slow).

Concretely, each prediction is written with a stable id, the window that produced it, the score, and the model version. An inspection resolves that id to one of three verdicts:

  • confirmed a true positive — a labeled failure example, gold for later Framing A/B.
  • false positive the case the inspector overturns — feeds threshold recalibration and becomes a hard negative.
  • missed a failure the model didn't flag, logged from post-hoc reality — the most valuable and rarest label.

That verdict log is the asset that compounds. It is what carries the system from anomaly detection (no labels) to horizon classification (many labels) without a rewrite, and it is the memory the agent in P5 eventually reasons over.

The advisor

An agent reads the predictions and the history, and recommends the fix.

Build
An LLM agent over the verdict log and past work orders (retrieval over history): given a fresh alert, it surfaces the most similar past cases, what the inspector found, what fixed it, and a confidence-weighted recommendation — never an unattended action.

Scaling down · keeping it lean

Because each phase wraps the one below, you can descend at will: a hardware-constrained edge box runs P1's kernel with no service; a quiet line can drop P4's fleet machinery and run a single P2 service; the agent in P5 is an advisor layer that can be switched off entirely, leaving P3 fully functional. The kernel never depends on the wrappers — only the reverse.

07 · Honest caveats

What will actually be hard

None of these are reasons not to build it — they're the things to design around from day one rather than discover at P4.

  • Cold start. You begin with no failures. This is why P0 leans on public data and the early framing is anomaly detection — the loop earns its labels over time.
  • Domain gap. A model that aces CWRU or KAIST will not transfer to your motors directly. Public data validates the approach and pipeline; a deployable model needs data collection on your own line.
  • Alert fatigue. The fastest way to kill the project is crying wolf. The calibration loop exists precisely to keep precision high enough that the floor keeps trusting it.
  • Feedback bias. Inspectors only verify what the model flags, so the labeled set skews toward the model's current blind spots. Log the occasional missed case and sample some healthy windows for verification to counter it.
  • Sensor alignment. Different channels sample at different rates and drift over time. Resample and align before windowing; monitor input drift once at P4 so a miscalibrated probe can't masquerade as a failing bearing.
Recommended first move

Spend a weekend on P0: window the KAIST temp/vibration/current set, train a small 1-D CNN, export one ONNX file. It costs nothing, proves the signals are separable on your exact sensor mix, and gives you the concrete feel to decide how far up the ladder to climb.
